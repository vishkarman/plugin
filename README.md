# Vishvakarma Plugin for DSH

Рабочая область дизайн-проектов для **DeepSeek Harness Desktop 0.2.1-rc.3 и 0.2.1-rc.5**.
Текущая версия плагина — `0.7.2-stage.1`; сборка использует SDK `0.2.1-rc.5`.
После установки пункт **Vishvakarma** появляется в левом меню DSH и открывает
Studio в центральной области. Команда `/vishvakarma` открывает ту же область;
кнопка «Рядом с чатом» открывает Studio в штатной Browser-панели.

Нужен отдельно запущенный [сервер](https://github.com/vishkarman/server) версии
`0.7.0-stage.1` с возможностью `workspace.projects.v1`. Плагин поставляется
самостоятельным пакетом: серверные исходники и общий workspace не требуются.
Он предоставляет агенту инструменты и скилл; проекты, ресурсы, права и сборки
хранит сервер. Модель и её подключение остаются в DSH.

## Сборка и установка

Node.js 24, pnpm 10.11.1. Команды выполняются **в корне этого репозитория**:

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm pack
```

Получится `vishkarman-plugin-0.7.2-stage.1.tgz`. В Desktop откройте
**Plugins → Add plugin**, укажите абсолютный путь к tarball и нажмите **Install**,
затем **Enable now**. В деталях пакета компонент `vishvakarma` должен иметь
статус **Running**. Одного Installed недостаточно. Если DSH запрашивает
перезапуск, перезапустите именно выбранный профиль.

Пакет включает собранные Host/Client, bundle patch, копию контрактов и скилл.
Соседний checkout сервера и исходники плагина для его работы не нужны.
SDK DSH предоставляется приложением, а не отдельной вложенной копией runtime.
При пересборке того же номера версии удалите старый bundle через **Uninstall**,
затем установите новый tarball. Удаление плагина не удаляет серверный проект;
неиспользуемый токен отзывается отдельно на сервере.

## Изолированный профиль разработки на macOS

Проверенный способ запуска второго экземпляра, не меняющий основной профиль:

```sh
VK_DEV="$HOME/Library/Application Support/Vishvakarma/dev"
mkdir -p "$VK_DEV/dsh-home" "$VK_DEV/electron"
DSH_HOME="$VK_DEV/dsh-home" \
  '/Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness' \
  --user-data-dir="$VK_DEV/electron"
```

Раздельны и DSH_HOME, и Electron user-data-dir. Установите bundle в этом окне.
Для обновления уже включённого bundle в этом профиле проверен также штатный CLI,
поставляемый внутри Desktop. Сначала соберите пакет командами выше, затем:

```sh
VK_DEV="$HOME/Library/Application Support/Vishvakarma/dev"
mkdir -p "$VK_DEV/artifacts"
cp vishkarman-plugin-0.7.2-stage.1.tgz "$VK_DEV/artifacts/"
DSH_HOME="$VK_DEV/dsh-home" \
  '/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh' \
  plugin --profile desktop add "$VK_DEV/artifacts/vishkarman-plugin-0.7.2-stage.1.tgz"
```

Если открытое окно не подхватило обновление, перезапустите только этот профиль
DSH прежней командой запуска. Проверяйте
версию и **Components → vishvakarma → Running** на странице Plugins: одного
обновления зависимости недостаточно. Этот способ сохраняет `cordis.patch.yml`
и credentials; основной профиль DSH не участвует.

Подключение к модели настраивается отдельно от токена Vishvakarma. Для работы
инструментов нужна модель DSH; для просмотра сохранённого проекта — только
сервер и браузер. Отладочные порты для обычного использования не нужны.

## Подключение к серверу

Получите приватный файл личного токена по README сервера. Для владельца остаётся
команда администратора `issue-token`; гость получает собственный токен после входа
в Studio: **Подключить DSH → Создать личный токен → Скачать токен для DSH**.
Сохраните скачанный `vishvakarma-dsh-token.json` в приватном каталоге (в примере
ниже — как `$VK_DEV/config/issued-token.json`). Токен владельца гостю не передаётся.
Подключение проверяет учётную запись
через `/api/v1/auth/me`, поэтому гостю не нужен доступ к исходному demo-проекту.
После установки bundle выполните команду из любого каталога:

```sh
VK_DEV="$HOME/Library/Application Support/Vishvakarma/dev"
chmod 600 "$VK_DEV/config/issued-token.json"
node "$VK_DEV/dsh-home/profiles/desktop/node_modules/@vishkarman/plugin/dist/connect.js" \
  http://127.0.0.1:3000 "$VK_DEV/config/issued-token.json"
```

Она проверяет установку и доступ, записывает токен в
`$VK_DEV/config/plugin-credentials.json` с правами 0600. Секрет не выводится.
Не передавайте токен в чат или в настройки плагина. Путь выше относится к
изолированному профилю; для другого профиля используйте его установленный пакет.
Из checkout та же команда доступна как `pnpm connect <origin> <token-file>`.

По умолчанию Host использует `http://127.0.0.1:3000` и указанный файл credentials.
Для другого адреса/файла добавьте **элемент в существующий массив**
`$DSH_HOME/profiles/desktop/cordis.patch.yml`, сохранив остальные настройки:

```yaml
- id: vishvakarma
  config:
    serverUrl: http://127.0.0.1:3100
    credentialsFile: /absolute/private/path/plugin-credentials.json
```

Проверено применение изменения через штатный loader DSH без пересборки bundle.
Разрешены только HTTP loopback origins без пути, query, userinfo и фрагмента.
После смены origin или installationId старый токен не отправляется: потребуется
запустить команду подключения для выбранной установки заново. Третий аргумент
`vishvakarma-connect` задаёт нестандартный выходной credentials-файл.
HTTP-редиректы запрещены. Файл токена должен иметь права 0600 и принадлежать
подходящей установке; адрес и токен не принимаются из аргументов инструментов.

## Работа

1. Откройте **Vishvakarma** слева и войдите своей учётной записью в Studio.
   Это отдельная HttpOnly-сессия; секрет Host в Client не передаётся. Для
   одинаковых прав в Studio и инструментах нужен токен той же учётной записи.
2. Создайте проект: пустой либо из HTML/CSS, React или React с 3D-сценой.
   Шаблон задаёт начальное содержимое, каждый проект получает собственный ID.
3. Загрузите файлы и изображение в Studio. Скопируйте контекст для DSH и передайте
   агенту задачу, например: «Используй скилл vishvakarma. В проекте с этим ID
   сделай страницу мастерской; используй assets/cover.png, сохрани и собери».
4. Агент читает актуальную ревизию, ресурсы, правила дизайна и возможности
   адаптеров, затем меняет цель или исходники. В Studio видны сохранение и сборка.
   Режим взаимодействия запускает поведение макета; Studio и готовый предпросмотр
   можно открыть отдельными действиями в браузере.

Проект и базовая ревизия всегда заданы явно в инструменте записи. Текущая
вкладка DSH/Studio не перенаправляет подготовленную команду. При чтении возвращается
`studioUrl` выбранного проекта (`/?project=<id>`); `entrypoint` определяет входной
макет, `targetId` выбирает дополнительный технический контекст адаптера.

| Инструмент | Назначение |
| --- | --- |
| `vishvakarma_adapter_project` | `list`: доступные проекты и шаблоны; `create`: новый проект; `open`/`read`: контекст; `update`: имя, описание, правила или точка входа |
| `vishvakarma_edit_target` | Поддержанная семантическая правка по adapterId, targetId, scope и property |
| `vishvakarma_write_files` | Создание, замена или удаление до 128 исходников по относительным путям |
| `vishvakarma_asset` | Сохранение ресурса в base64 до 8 MiB либо удаление; большие файлы удобнее загружать через Studio |
| `vishvakarma_build` | `start`: сборка точной сохранённой ревизии; `status`: результат и диагностика |
| `vishvakarma_read_project` / `vishvakarma_apply_change` | Совместимость с исходным demo первого прототипа, только для владельца |

Пример создания:

```json
{"request":{"action":"create","name":"Мастерская","template":"editorial"}}
```

Пример чтения выбранного проекта:

```json
{"request":{"action":"read","projectId":"ID из create или list","targetId":"необязательный ID из analysis.targets"}}
```

`open` и `read` ничего не создают. Создание доступно владельцу установки.
`list` возвращает `projects`, `templates` и `canCreate`; гость видит только свои
приглашённые проекты. Контекст содержит файлы с SHA-256, ресурсы с путём/MIME/размером,
точку входа, `analysis.targets`, `instructions`, `design`, текущую ревизию и `access`.
Правила дизайна принадлежат проекту; общая дизайн-система не навязывается.

`write_files` принимает полный UTF-8 исходник до 262144 символов на файл.
`expectedHash: null` означает, что файла нет в прочитанной базе; `content: null`
удаляет существующий файл. Папки отражаются в относительных путях, например
`src/App.tsx`. Ресурсы используют ту же структуру; в макете указывайте относительный
путь (`./assets/cover.png`), а не защищённый API-url из контекста. В React
предпочтителен импорт изображения относительно файла модуля и `src={imageUrl}`.
Строковый URL разрешается относительно HTML входа; `/assets/...` теряет приватный
префикс предпросмотра, поэтому абсолютный путь от корня сайта не подходит.

Runner исполняет поддержанные HTML/CSS и React, включая интерактивную 3D-сцену.
Он не устанавливает произвольные зависимости и не запускает package scripts или
пользовательские Vite-плагины. Возможности визуального редактирования определяются
анализом; незнакомая семантика доступна как исходный код.

## Сохранение и доступ

Оба инструмента правки поддерживают необязательный `action: "check" | "apply"`;
по умолчанию выполняется `apply`. Старая база допустима только если все затронутые
файлы целиком не изменились. Для семантической операции проверяется файл цели.
Правки внутри одного файла не сливаются, конфликт отклоняет пакет целиком.
`check` проверяет ситуацию сейчас, ничего не сохраняет и не резервирует.

Host создаёт `operationId`, если он не передан. После `check` или потери ответа
для повторения той же операции нужны возвращённый UUID, прежняя база и неизменный
payload. Новый осмысленный запрос получает новый ID. Создание проекта, изменение
метаданных и ресурса тоже используют стабильный `operationId`; автоматических
повторов записи нет. Ошибка содержит этот ID, чтобы результат можно было проверить.

При `CHANGE_CONFLICT` или `RESOURCE_CONFLICT` перечитайте источник и переоцените
правку; не подменяйте только базу/хеш, чтобы навязать прежний payload. `saved: true`
подтверждает сохранение, только `status: succeeded` — сборку. Старая успешная сборка
не является актуальным источником правки. Запрос ограничен восемью секундами;
потеря ответа или отмена не доказывает отсутствие записи.

Права проверяет сервер для каждого запроса: Viewer читает, Editor правит вручную,
а для изменений/check/сборки через DSH нужен `access.canUseAgent: true`.
`READ_ONLY`, `AGENT_FORBIDDEN`, `FORBIDDEN` требуют остановки, а не другого инструмента.
`PROJECT_NOT_FOUND` может означать отзыв доступа; перечитайте список, не создавайте
пропавший проект. `UNAUTHORIZED` — переподключение с личным токеном пользователя.
`RECONNECT_REQUIRED` — изменился адрес или installationId. `INCOMPATIBLE` — обновление
сервера: нужны `workspace.projects.v1`, `access.project-roles.v1` и для проверки
параллельных правок `adapters.checked-rebase.v1`.

Версия `0.7.0-stage.1` проверена 2026-11-01 в отдельном установленном профиле
локального веб-интерфейса DSH: постоянный пункт слева, вход в Studio, сохранение живого iframe при возврате
из чата, создание собственного проекта и загрузка PNG через интерфейс. Реальная
модель прочитала этот проект, создала лендинг с загруженным изображением и рабочим
диалогом, сохранила исходники и получила `succeeded` для той же ревизии. Проверены
открытие этого проекта в браузере и отдельный предпросмотр. На изолированном
сервере инструменты SDK проверены для вложенных файлов, создания/удаления,
ресурса, изменения метаданных, check/replay и неизменности адресата подготовленной
команды после чтения другого проекта.

Версия `0.7.2-stage.1` обновляет SDK сборки до `0.2.1-rc.5` и допускает
проверенные версии DSH `0.2.1-rc.3` и `0.2.1-rc.5`. В `0.7.0-stage.1` точные
peer-зависимости на `rc.3` блокировали установку после обновления DSH. Более
новые версии DSH требуют отдельной проверки; ограничение установщика не отключается.
Сервер остаётся `0.7.0-stage.1`, обновлять его для этого исправления не нужно.
Нативное окно Desktop использует `dsh-app://app`, поэтому здесь Studio открывается
через изолированный webview, а не iframe с требованием совпадения локальных имён.
На `rc.5` отдельно проверены статус Running, настоящее окно `dsh-app://app`, ввод
пароля и вход, сохранённый макет с PNG, открытие интерактивного диалога физическим
кликом, передача ссылки браузеру и сохранение живой Studio при переходе в чат.

## Интеграция с DSH

Client регистрирует штатные публичные слоты SDK 0.2.1-rc.3/rc.5:
`sidebar.panellist` — постоянный пункт слева, `main` — центральную область и
`shell.overlay` — живую поверхность Studio. Область измеряется через собственный
anchor и ResizeObserver; DOM/CSS DSH не меняются. Studio остаётся смонтированной
при переходе к чату или другой сессии, поэтому введённый текст и неподтверждённые
правки не теряются из-за навигации DSH. Возвращение в Vishvakarma показывает ту же Studio.

URL и доступность Studio приходят из Host через Typert Remote. Токен хранится
только в приватном файле Host; Studio использует отдельную браузерную сессию.
В веб-интерфейсе DSH iframe требует совпадения локального имени DSH/Studio
(`127.0.0.1` по умолчанию) и разрешённого сервером frame ancestor. При разных
именах предлагается Browser-панель. К нативному окну Desktop это требование
не относится. Серверная настройка iframe описана в README сервера.
«Рядом с чатом» использует `sidebarRight.openTab('browser', ...)` и требует Browser-пакета.

В Desktop компонент использует публичный `DesktopBrowserBridge` из SDK Browser:
`acquire`, `release` и `onOpenRequested`. DSH выдаёт разрешение на гостевое окно
и сам задаёт sandbox, запрет Node.js, изоляцию контекста и отдельное хранилище
браузерной сессии. Плагин не меняет эти ограничения и не внедряет код в Studio.
Веб-интерфейс DSH сохраняет iframe-вариант. Ссылки на отдельный просмотр из
нативной Studio передаются системному браузеру через окно DSH.
DSH запрещает скачивания в гостевом браузере; для скачивания токена или исходников
откройте ту же Studio в системном браузере. Browser-панель DSH имеет то же ограничение.

Host регистрирует семь инструментов и файловый provider скилла из установленного
пакета. React берётся из DSH Client runtime; копия React в клиентский bundle не
включается. Контракты `contracts/index.ts`, `runner.ts`, `adapters.ts`, `access.ts`
копируются из сервера без редактирования; `source.json` фиксирует SHA-256 и версию.
Сборка проверяет эти хеши. Код сервера во время работы или сборки не импортируется.
