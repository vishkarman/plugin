# Vishvakarma Plugin for DSH

Рабочая область дизайн-проектов для **DeepSeek Harness Desktop 0.2.1-rc.3 и 0.2.1-rc.5**.
Текущая версия плагина — `0.9.3-stage.3`; сборка использует SDK `0.2.1-rc.5`.
После установки пункт **Vishvakarma** появляется в левом меню DSH и открывает
Studio в центральной области. Команда `/vishvakarma` открывает ту же область;
кнопка с иконкой разделённого окна открывает Studio рядом с чатом в штатной Browser-панели.
Кнопки в шапке имеют подсказки при наведении: «Обновление плагина»,
«Открыть Studio рядом с чатом», «Закрыть Studio и вернуться к чату».
Последняя кнопка с крестиком возвращает чат в центральную область; Studio остаётся открытой в фоне.
Нажмите Vishvakarma слева, чтобы вернуться к той же рабочей области.

В Desktop рядом с обновлением плагина есть отдельная кнопка **«Перезагрузить Studio»**
с одной круговой стрелкой. Она загружает актуальный интерфейс с уже обновлённого
сервера без перезапуска DSH, сохраняя текущий адрес проекта и браузерную сессию.
Сначала появляется подтверждение; «Отмена» и Escape оставляют страницу нетронутой.
Несохранённые поля и состояние предпросмотра могут сброситься — сохраните их перед
перезагрузкой. Кнопка недоступна во время загрузки страницы. Она не устанавливает
сервер или плагин: серверные UI-изменения становятся видимы после перезагрузки,
а установка новой версии плагина остаётся отдельным действием.

Нужен отдельно запущенный [сервер](https://github.com/vishkarman/server) версии
`0.9.0-stage.3` для новых инструментов редактора. Прежние возможности продолжают проверяться отдельно. Плагин поставляется
самостоятельным пакетом: серверные исходники и общий workspace не требуются.
Он предоставляет агенту инструменты и скилл; проекты, ресурсы, права и сборки
хранит сервер. Модель и её подключение остаются в DSH.

## Сборка и установка

Node.js 24, pnpm 10.11.1. Команды выполняются **в корне этого репозитория**:

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm pack
```

Получится `vishkarman-plugin-0.9.3-stage.3.tgz`. В Desktop откройте
**Plugins → Add plugin**, укажите абсолютный путь к tarball и нажмите **Install**,
затем **Enable now**. В деталях пакета компонент `vishvakarma` должен иметь
статус **Running**. Одного Installed недостаточно. Если DSH запрашивает
перезапуск, перезапустите именно выбранный профиль.

Пакет включает собранные Host/Client, bundle patch, копию контрактов и скилл.
Соседний checkout сервера и исходники плагина для его работы не нужны.
SDK DSH предоставляется приложением, а не отдельной вложенной копией runtime.
При пересборке того же номера версии удалите старый bundle через **Uninstall**,
затем установите новый tarball. Удаление плагина не удаляет серверный проект;
неиспользуемый токен отзывается отдельно на сервере.

## Обновление кнопкой в DSH

В **Plugins → @vishkarman/plugin** и в шапке рабочей области Vishvakarma есть
кнопка **«Обновление плагина»** (в шапке — иконка круговых стрелок). Она открывает одно окно с установленной и
работающей версиями, источником обновления и результатом последней операции.
Цвета окна следуют светлой или тёмной теме DSH.
Кнопка проверена в Desktop `0.2.1-rc.5`.

Пока доступен локальный источник для разработки. Настройте его один раз:

1. Откройте **«Источник обновлений»**, включите **«Режим разработчика»**.
2. Укажите абсолютный путь к checkout репозитория `plugin` с установленными
   зависимостями (`pnpm install --frozen-lockfile`) и сохраните настройки.
3. Нажмите **«Проверить обновление»**, затем **«Обновить плагин»**.

Сборка запускает код выбранного checkout: используйте собственные доверенные
исходники. Берутся сохранённые файлы, включая незакоммиченные изменения;
автоматического `git pull` нет. Сборка получает уникальную local-версию.
Если исходники совпадают с установленной local-сборкой, повторная установка
не предлагается. Если они изменились после проверки, нужна новая проверка.

Синий кружок на иконке означает, что локальные исходники отличаются от установленной
сборки. Он обновляется при открытии Studio/карточки плагина и возвращении фокуса в
DSH; сравнение кешируется на 30 секунд. Читаются только входные файлы сборки,
без `node_modules`, `dist`, наблюдателей файлов, фоновых таймеров, сборки и запросов
к серверу или реестру пакетов. При закрытом окне обновления периодического опроса нет.
Это сигнал об изменениях, а не подтверждение совместимости: её проверяет кнопка
«Проверить обновление». При отключённом режиме разработчика, недоступной папке или
отсутствии сведений об установленной local-сборке кружок не показывается;
ручная проверка остаётся доступной. После успешного обновления кружок исчезает.

Профиль берётся из текущего окна DSH, включая его `DSH_HOME`, а не из сохранённого
назначения терминальной команды. Используются действующие настройки подключения
плагина и штатный runtime/package manager DSH. Сначала проверяются DSH, API и
возможности сервера; затем подготовленный архив устанавливает менеджер DSH.
Сервер, Runner и проекты эта кнопка не обновляет.

Закрывать DSH перед обновлением кнопкой не нужно. Если DSH может применить пакет
сразу, он перезагрузит плагин; открытое окно обновления восстановится и покажет
результат. Иначе появится просьба перезапустить DSH. Закрытие окна обновления не
отменяет операцию: результат можно посмотреть, открыв его снова. Закрытие всего
приложения может прервать работу; после запуска проверьте результат и повторите
проверку при сообщении о прерывании.

Настройки источника сохраняются в `vishvakarma-updates.json` внутри текущего
профиля. Результат и приватные логи — в каталоге профиля внутри кеша
`Vishvakarma/plugin-updates`; путь к логу доступен в окне. Настройки подключения,
credentials и состояние включения пакета сохраняются. Проверенная установка
файлов и результат применения DSH показываются отдельно от необходимости
перезапуска.

Загрузка готовых выпусков из npm/GitHub пока не подключена. Для неё можно
добавить источник пакета, сохранив общее окно и установку. Версию с этой кнопкой
первый раз установите архивом или терминальной командой ниже.

1 ноября 2026 в отдельном нативном DSH `rc.5` проверены обе точки входа,
сохранение режима разработчика и пути, обновление работающего плагина через

Настройки подключения и credentials сохранились; повторная проверка распознала
уже установленные исходники. Несовместимые возможности сервера и изменение

## Обновление локальной сборки одной командой

После первой установки плагина используйте `pnpm update:dsh` из корня этого
репозитория. Перед обновлением закройте выбранный экземпляр DSH. При первом запуске
явно выберите существующий профиль и его DSH_HOME. Для обычного Desktop,
запущенного без отдельного `DSH_HOME`:

```sh
pnpm update:dsh \
  --dsh-home "$HOME/.dsh" \
  --profile desktop
```

Если нужно обновить отдельный экземпляр разработки, вместо `$HOME/.dsh` укажите
`$HOME/Library/Application Support/Vishvakarma/dev/dsh-home`. Это разные установки
плагина: обновление одной не обновляет другую. Команда печатает назначение и
установленную версию перед началом работы. Один перезапуск DSH пакет не обновляет.

После успешной установки выбор сохраняется в локальном `.dsh-update.local.json`
(исключён из Git). Дальнейшие обновления:

```sh
pnpm update:dsh
```

Команда проверяет DSH и возможности запущенного сервера, делает снимок исходников,
собирает и упаковывает его во временной папке, затем вызывает штатный
`dsh plugin --profile <имя> add <архив>`. Она не изменяет исходную версию в
`package.json`, рабочий `dist/` или исходники. Если файлы меняются во время сборки,
установка отменяется: повторите команду после сохранения изменений.

Каждый архив получает уникальную локальную версию, например
`0.9.1-stage.3.local.<время>.<pid>`. Для исходной стабильной версии используется
предварительная local-сборка следующего patch-релиза; установленный более новый
релиз не понижается автоматически. Такая нумерация устраняет повторное использование
старого пакета из кеша. Это команда локального обновления, она не публикует пакет
в npm и не создаёт Git-коммитов/тегов.

Настройки берутся из patch-файлов выбранного профиля и DSH_HOME. Проверяются
диапазоны DSH SDK в `peerDependencies`, API и возможности из поставляемых
контрактов; остальные peer-зависимости проверяет штатный установщик. Адрес сервера
определяется из настроек Vishvakarma; для стандартной конфигурации это
`http://127.0.0.1:3000`. Сервер должен работать и предоставлять возможности новой
сборки. Токен для этой проверки не отправляется. Произвольные дополнительные
`--patch` из команды запуска DSH этим помощником не учитываются.

Профиль не создаётся и не сбрасывается; плагин должен быть установлен заранее.
Команда проверяет сохранность patch-файлов, settings и credentials и не
перезаписывает их. Сохранённое включение/отключение bundle остаётся в профиле.
При ошибке установщика смотрите приватный лог: команда не объявляет обновление
успешным и не восстанавливает старые настройки поверх возможных чужих правок.

После установки сверяются версия и основные файлы пакета. Запущенный DSH
автоматически не перезапускается: перезапустите выбранный профиль и проверьте
**Plugins → Vishvakarma → Components → Running**. Проверенная установка файлов
сама по себе не подтверждает запуск компонента. Для выключенного bundle команда
сохраняет выключенное состояние.

Архивы, приватные логи и запись последней установки сохраняются на macOS в
`~/Library/Caches/Vishvakarma/plugin-updates/`, на других системах — в
`~/.cache/vishvakarma/plugin-updates/`. Это кеш сборок, не резервная копия проектов.
Обновляется только явно выбранный или ранее запомненный профиль DSH.

Дополнительные команды:

```sh
pnpm update:dsh --check   # проверить выбранный профиль, DSH и сервер без установки
pnpm update:dsh --help
```

Другой CLI задаётся через `--dsh /absolute/path/to/dsh`; на macOS по умолчанию
используется CLI установленного DeepSeek Harness Desktop, иначе — `dsh` из PATH.
При смене назначения всегда указывайте `--dsh-home` и `--profile` вместе.
Проверка с `--check` не меняет запомненное назначение. Требуются Node.js 24,
pnpm и установленные зависимости этого репозитория.

2026-11-01: в отдельном временном профиле установленного DSH `0.2.1-rc.5`
проверены полная установка, повторное обновление без параметров с новым номером,
сохранение выключенного bundle и настроек/credentials. Несовместимый DSH,
недостаточные возможности и недоступность сервера остановили установку без
изменения установленного пакета и выбранного назначения. Запуск компонента в UI
в этих проверках не выполнялся.

## Изолированный профиль разработки на macOS

Проверенный способ запуска второго экземпляра, не меняющий основной профиль:

```sh
VK_DEV="$HOME/Library/Application Support/Vishvakarma/dev"
mkdir -p "$VK_DEV/dsh-home" "$VK_DEV/electron"
DSH_HOME="$VK_DEV/dsh-home" \
  '/Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness' \
  --user-data-dir="$VK_DEV/electron"
```

Раздельны и DSH_HOME, и Electron user-data-dir. Установите bundle в этом окне.
Для обновления уже включённого bundle в этом профиле проверен также штатный CLI,
поставляемый внутри Desktop. Сначала соберите пакет командами выше, затем:

```sh
VK_DEV="$HOME/Library/Application Support/Vishvakarma/dev"
mkdir -p "$VK_DEV/artifacts"
cp vishkarman-plugin-0.9.1-stage.3.tgz "$VK_DEV/artifacts/"
DSH_HOME="$VK_DEV/dsh-home" \
  '/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh' \
  plugin --profile desktop add "$VK_DEV/artifacts/vishkarman-plugin-0.9.1-stage.3.tgz"
```

Если открытое окно не подхватило обновление, перезапустите только этот профиль
DSH прежней командой запуска. Проверяйте
версию и **Components → vishvakarma → Running** на странице Plugins: одного
обновления зависимости недостаточно. Этот способ сохраняет `cordis.patch.yml`
и credentials; основной профиль DSH не участвует.

Подключение к модели настраивается отдельно от токена Vishvakarma. Для работы
инструментов нужна модель DSH; для просмотра сохранённого проекта — только
сервер и браузер. Отладочные порты для обычного использования не нужны.

## Подключение к серверу

Получите приватный файл личного токена по README сервера. Для владельца остаётся
команда администратора `issue-token`; гость получает собственный токен после входа
в Studio: **Подключить DSH → Создать личный токен → Скачать токен для DSH**.
Сохраните скачанный `vishvakarma-dsh-token.json` в приватном каталоге (в примере
ниже — как `$VK_DEV/config/issued-token.json`). Токен владельца гостю не передаётся.
Подключение проверяет учётную запись
через `/api/v1/auth/me`, поэтому гостю не нужен доступ к исходному demo-проекту.
После установки bundle выполните команду из любого каталога:

```sh
VK_DEV="$HOME/Library/Application Support/Vishvakarma/dev"
chmod 600 "$VK_DEV/config/issued-token.json"
node "$VK_DEV/dsh-home/profiles/desktop/node_modules/@vishkarman/plugin/dist/connect.js" \
  http://127.0.0.1:3000 "$VK_DEV/config/issued-token.json"
```

Она проверяет установку и доступ, записывает токен в
`$VK_DEV/config/plugin-credentials.json` с правами 0600. Секрет не выводится.
Не передавайте токен в чат или в настройки плагина. Путь выше относится к
изолированному профилю; для другого профиля используйте его установленный пакет.
Из checkout та же команда доступна как `pnpm connect <origin> <token-file>`.

По умолчанию Host использует `http://127.0.0.1:3000` и указанный файл credentials.
Для другого адреса/файла добавьте **элемент в существующий массив**
`$DSH_HOME/profiles/desktop/cordis.patch.yml`, сохранив остальные настройки:

```yaml
- id: vishvakarma
  config:
    serverUrl: http://127.0.0.1:3100
    credentialsFile: /absolute/private/path/plugin-credentials.json
```

Проверено применение изменения через штатный loader DSH без пересборки bundle.
Разрешены только HTTP loopback origins без пути, query, userinfo и фрагмента.
После смены origin или installationId старый токен не отправляется: потребуется
запустить команду подключения для выбранной установки заново. Третий аргумент
`vishvakarma-connect` задаёт нестандартный выходной credentials-файл.
HTTP-редиректы запрещены. Файл токена должен иметь права 0600 и принадлежать
подходящей установке; адрес и токен не принимаются из аргументов инструментов.

## Работа

1. Откройте **Vishvakarma** слева и войдите своей учётной записью в Studio.
   Это отдельная HttpOnly-сессия; секрет Host в Client не передаётся. Для
   одинаковых прав в Studio и инструментах нужен токен той же учётной записи.
2. Создайте проект: пустой либо из HTML/CSS, React или React с 3D-сценой.
   Шаблон задаёт начальное содержимое, каждый проект получает собственный ID.
3. Загрузите файлы и изображение в Studio. Скопируйте контекст для DSH и передайте
   агенту задачу, например: «Используй скилл vishvakarma. В проекте с этим ID
   сделай страницу мастерской; используй assets/cover.png, сохрани и собери».
4. Агент читает актуальную ревизию, ресурсы, правила дизайна и возможности
   адаптеров, затем меняет цель или исходники. В Studio видны сохранение и сборка.
   Режим взаимодействия запускает поведение макета; Studio и готовый предпросмотр
   можно открыть отдельными действиями в браузере.

Проект и базовая ревизия всегда заданы явно в инструменте записи. Текущая
вкладка DSH/Studio не перенаправляет подготовленную команду. При чтении возвращается
`studioUrl` выбранного проекта (`/?project=<id>`); `entrypoint` определяет входной
макет, `targetId` выбирает дополнительный технический контекст адаптера.

| Инструмент | Назначение |
| --- | --- |
| `vishvakarma_adapter_project` | `list`: доступные проекты и шаблоны; `create`: новый проект; `open`/`read`: контекст; `update`: имя, описание, правила или точка входа |
| `vishvakarma_edit_target` | Поддержанная семантическая правка по adapterId, targetId, scope и property |
| `vishvakarma_write_files` | Создание, замена или удаление до 128 исходников по относительным путям |
| `vishvakarma_asset` | Сохранение ресурса в base64 до 8 MiB либо удаление; большие файлы удобнее загружать через Studio |
| `vishvakarma_history` | `list/read`: история и точная версия; `label`: название; `restore`: новая ревизия из выбранной версии |
| `vishvakarma_comments` | Обсуждения с ответами, статусом привязки и курсором следующей страницы |
| `vishvakarma_export` | `start`: source/web выбранной версии; `status`: готовность и ссылка скачивания в браузере |
| `vishvakarma_build` | `start`: сборка точной сохранённой ревизии; `status`: результат и диагностика |
| `vishvakarma_read_project` / `vishvakarma_apply_change` | Совместимость с исходным demo первого прототипа, только для владельца |

Пример создания:

```json
{"request":{"action":"create","name":"Мастерская","template":"editorial"}}
```

Пример чтения выбранного проекта:

```json
{"request":{"action":"read","projectId":"ID из create или list","targetId":"необязательный ID из analysis.targets"}}
```

`open` и `read` ничего не создают. Создание доступно владельцу установки.
`list` возвращает `projects`, `templates` и `canCreate`; гость видит только свои
приглашённые проекты. Контекст содержит файлы с SHA-256, ресурсы с путём/MIME/размером,
точку входа, `analysis.targets`, `instructions`, `design`, текущую ревизию и `access`.
Правила дизайна принадлежат проекту; общая дизайн-система не навязывается.

`write_files` принимает полный UTF-8 исходник до 262144 символов на файл.
`expectedHash: null` означает, что файла нет в прочитанной базе; `content: null`
удаляет существующий файл. Папки отражаются в относительных путях, например
`src/App.tsx`. Ресурсы используют ту же структуру; в макете указывайте относительный
путь (`./assets/cover.png`), а не защищённый API-url из контекста. В React
предпочтителен импорт изображения относительно файла модуля и `src={imageUrl}`.
Строковый URL разрешается относительно HTML входа; `/assets/...` теряет приватный
префикс предпросмотра, поэтому абсолютный путь от корня сайта не подходит.

Runner исполняет поддержанные HTML/CSS и React, включая интерактивную 3D-сцену.
Он не устанавливает произвольные зависимости и не запускает package scripts или
пользовательские Vite-плагины. Возможности визуального редактирования определяются
анализом; незнакомая семантика доступна как исходный код.

## Версии, обсуждения и результат

Пользователь работает с историей и комментариями в той же Studio. Агент читает
их через `vishvakarma_history` и `vishvakarma_comments`; правила восстановления
и изменившихся привязок описаны в скилле. `restore` выполняется только по поручению
пользователя после чтения выбранной и текущей версии, с явной baseRevisionId.

`vishvakarma_export` принимает `action: start`, projectId, revisionId и kind:
`source` содержит исходники и ресурсы, `web` собирает самостоятельный сайт без
редакторского кода. После `ready` передайте browserUrl пользователю. Для скачивания
он входит в браузере; токен не переносится в URL или Client. Исходники доступны
всем участникам, для сборки web требуется canUseAgent. Динамика React/3D сохраняется
в поддержанном Runner, внешние серверы и произвольные npm-зависимости не включаются.

## Сохранение и доступ

Оба инструмента правки поддерживают необязательный `action: "check" | "apply"`;
по умолчанию выполняется `apply`. Старая база допустима только если все затронутые
файлы целиком не изменились. Для семантической операции проверяется файл цели.
Правки внутри одного файла не сливаются, конфликт отклоняет пакет целиком.
`check` проверяет ситуацию сейчас, ничего не сохраняет и не резервирует.

Host создаёт `operationId`, если он не передан. После `check` или потери ответа
для повторения той же операции нужны возвращённый UUID, прежняя база и неизменный
payload. Новый осмысленный запрос получает новый ID. Создание проекта, изменение
метаданных и ресурса тоже используют стабильный `operationId`; автоматических
повторов записи нет. Ошибка содержит этот ID, чтобы результат можно было проверить.

При `CHANGE_CONFLICT` или `RESOURCE_CONFLICT` перечитайте источник и переоцените
правку; не подменяйте только базу/хеш, чтобы навязать прежний payload. `saved: true`
подтверждает сохранение, только `status: succeeded` — сборку. Старая успешная сборка
не является актуальным источником правки. Запрос ограничен восемью секундами;
потеря ответа или отмена не доказывает отсутствие записи.

Права проверяет сервер для каждого запроса: Viewer читает, Commenter обсуждает в Studio, Editor правит вручную,
а для изменений/check/сборки через DSH нужен `access.canUseAgent: true`.
`READ_ONLY`, `AGENT_FORBIDDEN`, `FORBIDDEN` требуют остановки, а не другого инструмента.
`PROJECT_NOT_FOUND` может означать отзыв доступа; перечитайте список, не создавайте
пропавший проект. `UNAUTHORIZED` — переподключение с личным токеном пользователя.
`RECONNECT_REQUIRED` — изменился адрес или installationId. `INCOMPATIBLE` — обновление
сервера: нужны `product.history-comments-export.v1`, `workspace.projects.v1`, `access.project-roles.v1` и для проверки
параллельных правок `adapters.checked-rebase.v1`.

## Интеграция с DSH

Client регистрирует штатные публичные слоты SDK 0.2.1-rc.3/rc.5:
`sidebar.panellist` — постоянный пункт слева, `main` — центральную область и
`shell.overlay` — живую поверхность Studio. Область измеряется через собственный
anchor и ResizeObserver; DOM/CSS DSH не меняются. Studio остаётся смонтированной
при переходе к чату или другой сессии, поэтому введённый текст и неподтверждённые
правки не теряются из-за навигации DSH. Возвращение в Vishvakarma показывает ту же Studio.

URL и доступность Studio приходят из Host через Typert Remote. Токен хранится
только в приватном файле Host; Studio использует отдельную браузерную сессию.
В веб-интерфейсе DSH iframe требует совпадения локального имени DSH/Studio
(`127.0.0.1` по умолчанию) и разрешённого сервером frame ancestor. При разных
именах предлагается Browser-панель. К нативному окну Desktop это требование
не относится. Серверная настройка iframe описана в README сервера.
«Открыть Studio рядом с чатом» требует Browser-пакета и выбранного чата. Сначала
плагин переключает центральную область на чат, затем после его отрисовки вызывает
`sidebarRight.openTab('browser', ...)`. Если чат не выбран, Studio остаётся видимой
и объясняет, что нужно открыть или создать чат. В Desktop передаётся текущий адрес
Studio с выбранным проектом. Browser — отдельное представление, поэтому несохранённое
состояние центральной Studio туда не переносится; оно остаётся в центральной области.

В Desktop компонент использует публичный `DesktopBrowserBridge` из SDK Browser:
`acquire`, `release` и `onOpenRequested`. DSH выдаёт разрешение на гостевое окно
и сам задаёт sandbox, запрет Node.js, изоляцию контекста и отдельное хранилище
браузерной сессии. Плагин не меняет эти ограничения и не внедряет код в Studio.
Веб-интерфейс DSH сохраняет iframe-вариант. Ссылки на отдельный просмотр из
нативной Studio передаются системному браузеру через окно DSH.
DSH запрещает скачивания в гостевом браузере. Studio этапа 2 открывает экспорт
в системном браузере; локальный черновик или токен передаётся туда по явной кнопке
через личную ссылку сроком 15 минут. Войдите той же учётной записью. Без связи
доступно ручное копирование текста. Browser-панель DSH имеет то же ограничение.
В подтверждениях Studio используются собственные диалоги; sandbox DSH не меняется.

Host регистрирует одиннадцать инструментов и файловый provider скилла из установленного
пакета. React берётся из DSH Client runtime; копия React в клиентский bundle не
включается. Контракты `contracts/index.ts`, `runner.ts`, `adapters.ts`, `access.ts`, `product.ts`
копируются из сервера без редактирования; `source.json` фиксирует SHA-256 и версию.
Сборка проверяет эти хеши. Код сервера во время работы или сборки не импортируется.
