# Vishvakarma Plugin for DSH

Устанавливаемый bundle прототипа прав и приглашений Vishvakarma для **DeepSeek Harness
Desktop 0.2.1-rc.3**. Шесть инструментов работают с исходниками и целями трёх
дизайн-примеров и сохраняют совместимость с исходным demo-проектом. Команда
`/vishvakarma` открывает серверную Studio во встроенной Browser-панели.
Скилл `vishvakarma` загружается из установленного пакета через штатный provider.

Нужен отдельно запущенный [сервер](https://github.com/vishkarman/server).
Плагин не запускает сервер, не хранит проект и не генерирует его без DSH.
Примеры охватывают HTML/CSS и React с интерактивной 3D-сценой. Редактировать
можно три файла выбранного примера (`index.html`, `main.tsx`, `style.css`); это
ещё не импорт произвольного репозитория и не полноценный визуальный редактор.
Плагин учитывает доступ владельца, Viewer и Editor; право агента на изменения
выдаётся отдельно от ручного редактирования в Studio.

## Сборка и установка

Node.js 24, pnpm 10.11.1. Команды выполняются **в корне этого репозитория**:

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm pack
```

Получится `vishkarman-plugin-0.6.0-prototype.6.tgz`. В Desktop откройте
**Plugins → Add plugin**, укажите абсолютный путь к tarball и нажмите **Install**,
затем **Enable now**. В деталях пакета компонент `vishvakarma` должен иметь
статус **Running**. Одного Installed недостаточно. Если DSH запрашивает
перезапуск, перезапустите именно выбранный профиль.

Пакет включает собранные Host/Client, bundle patch, копию контрактов и скилл.
Соседний checkout сервера и исходники плагина для его работы не нужны.
SDK DSH предоставляется приложением, а не отдельной вложенной копией runtime.
При пересборке того же номера версии удалите старый bundle через **Uninstall**,
затем установите новый tarball. Удаление плагина не удаляет серверный проект;
неиспользуемый токен отзывается отдельно на сервере.

## Изолированный профиль разработки на macOS

Проверенный способ запуска второго экземпляра, не меняющий основной профиль:

```sh
VK_DEV="$HOME/Library/Application Support/Vishvakarma/dev"
mkdir -p "$VK_DEV/dsh-home" "$VK_DEV/electron"
DSH_HOME="$VK_DEV/dsh-home" \
  '/Applications/DeepSeek Harness.app/Contents/MacOS/DeepSeek Harness' \
  --user-data-dir="$VK_DEV/electron"
```

Раздельны и DSH_HOME, и Electron user-data-dir. Установите bundle в этом окне.
Для обновления уже включённого bundle в этом профиле проверен также штатный CLI,
поставляемый внутри Desktop. Сначала соберите пакет командами выше, затем:

```sh
VK_DEV="$HOME/Library/Application Support/Vishvakarma/dev"
mkdir -p "$VK_DEV/artifacts"
cp vishkarman-plugin-0.6.0-prototype.6.tgz "$VK_DEV/artifacts/"
DSH_HOME="$VK_DEV/dsh-home" \
  '/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh' \
  plugin --profile desktop add "$VK_DEV/artifacts/vishkarman-plugin-0.6.0-prototype.6.tgz"
```

Если открытое окно не подхватило обновление, перезапустите только этот профиль
DSH прежней командой запуска. Проверяйте
версию и **Components → vishvakarma → Running** на странице Plugins: одного
обновления зависимости недостаточно. Этот способ сохраняет `cordis.patch.yml`
и credentials; основной профиль DSH не участвует. Проверено обновление с
прототипа 1 до версии 0.3.0-prototype.3 и состояние Running после перезапуска.
2026-11-01 отдельный Desktop-профиль обновлён с 0.3 до 0.5.0-prototype.5;
новая версия имеет статус Running. Реальная модель загрузила скилл, прочитала
`scene` и вызвала `vishvakarma_edit_target` с `action: check`, получив `ready`.
Сохранение и сборка в этом проходе не запрашивались; исходники не изменились.

Подключение к модели настраивается отдельно от токена Vishvakarma. Для работы
инструментов нужна модель DSH; для просмотра сохранённого проекта — только
сервер и браузер. Отладочные порты для обычного использования не нужны.

## Подключение к серверу

Получите приватный файл личного токена по README сервера. Для владельца остаётся
команда администратора `issue-token`; гость получает собственный токен после входа
в Studio: **Подключить DSH → Создать личный токен → Скачать токен для DSH**.
Сохраните скачанный `vishvakarma-dsh-token.json` в приватном каталоге (в примере
ниже — как `$VK_DEV/config/issued-token.json`). Токен владельца гостю не передаётся.
Подключение проверяет учётную запись
через `/api/v1/auth/me`, поэтому гостю не нужен доступ к исходному demo-проекту.
После установки bundle выполните команду из любого каталога:

```sh
VK_DEV="$HOME/Library/Application Support/Vishvakarma/dev"
chmod 600 "$VK_DEV/config/issued-token.json"
node "$VK_DEV/dsh-home/profiles/desktop/node_modules/@vishkarman/plugin/dist/connect.js" \
  http://127.0.0.1:3000 "$VK_DEV/config/issued-token.json"
```

Она проверяет установку и доступ, записывает токен в
`$VK_DEV/config/plugin-credentials.json` с правами 0600. Секрет не выводится.
Не передавайте токен в чат или в настройки плагина. Путь выше относится к
изолированному профилю; для другого профиля используйте его установленный пакет.
Из checkout та же команда доступна как `pnpm connect <origin> <token-file>`.

По умолчанию Host использует `http://127.0.0.1:3000` и указанный файл credentials.
Для другого адреса/файла добавьте **элемент в существующий массив**
`$DSH_HOME/profiles/desktop/cordis.patch.yml`, сохранив остальные настройки:

```yaml
- id: vishvakarma
  config:
    serverUrl: http://127.0.0.1:3100
    credentialsFile: /absolute/private/path/plugin-credentials.json
```

Проверено применение изменения через штатный loader DSH без пересборки bundle.
Разрешены только HTTP loopback origins без пути, query, userinfo и фрагмента.
После смены origin или installationId старый токен не отправляется: потребуется
запустить команду подключения для выбранной установки заново. Третий аргумент
`vishvakarma-connect` задаёт нестандартный выходной credentials-файл.
HTTP-редиректы запрещены. Файл токена должен иметь права 0600 и принадлежать
подходящей установке; адрес и токен не принимаются из аргументов инструментов.

## Работа

1. В чате DSH выполните `/vishvakarma` — действие «Открыть Vishvakarma».
2. В открытой Studio войдите своей учётной записью (`owner` или гостя). Это
   отдельная HttpOnly-сессия браузера; токен плагина в Client не передаётся.
   Для одинакового доступа в Studio и инструментах нужен токен той же учётной записи.
3. Попросите: «Используй скилл vishvakarma. Открой пример editorial и замени
   заголовок на “Новая история”, сохрани существующее оформление и собери результат».
4. Агент получает контекст проекта, выбирает доступную операцию или меняет
   исходник, сохраняет ревизию и запускает сборку. В Studio выберите тот же пример.

Для 3D можно попросить: «В примере scene измени цвет объекта через доступную
операцию адаптера и собери результат; остальную страницу и вращение сохрани».
Инструмент чтения возвращает конкретные цели и возможности; агент не должен
угадывать их идентификаторы или обещать неподдерживаемую операцию.

Для версии `0.3.0-prototype.3` на Desktop 0.2.1-rc.3 ранее проверен полный
проход модели: скилл, контекст адаптеров, правка материала, hover-поведения
и кнопки, сохранение и успешная сборка. Проверки новых условий применения
версии `0.5.0-prototype.5` описаны ниже отдельно.

| Инструмент | Результат |
| --- | --- |
| `vishvakarma_adapter_project` | `list`: доступные проекты и права; `open`: открыть существующий (только владелец может впервые создать пример); `read`: исходники, хеши, ревизия, цели, инструкции адаптеров и `access` |
| `vishvakarma_edit_target` | Семантическая операция с явными adapterId, property и scope; `action: check` проверяет, `apply` сохраняет |
| `vishvakarma_write_files` | Проверка или замена от одного до трёх исходников с базовой ревизией и SHA-256 каждого файла |
| `vishvakarma_build` | `start`: сборка сохранённой ревизии; `status`: состояние и диагностика сборки |
| `vishvakarma_read_project` | Только владельцу: исходный demo-проект первого прототипа, HTML и ревизия |
| `vishvakarma_apply_change` | Только владельцу: замена текста `#demo-title` исходного demo-проекта |

`list` для гостя возвращает только уже существующие проекты с действующим
доступом. `open` гостя выполняет GET и не создаёт пример. Для владельца доступны
три шаблона, которые создаются при первом `open`. Поле `canCreateExamples`
в списке показывает эту возможность.

Список и контекст содержат `access`: `role` (`owner`, `viewer`, `editor`),
`canEdit`, `canManage`, `canUseAgent`. Viewer может читать проект и состояние
доступных сборок. Editor может вручную править проект в Studio, но для изменений
через DSH, проверки `check` и запуска сборки нужен **`canUseAgent: true`** —
отдельное разрешение владельца. Права перепроверяются сервером на каждом запросе;
старый прочитанный контекст не сохраняет отозванный доступ.

`READ_ONLY` означает роль Viewer; `AGENT_FORBIDDEN` — у Editor нет разрешения
агента; `FORBIDDEN` — операция недоступна. Повтора или обходного инструмента нет:
агент объясняет недостающее право. `PROJECT_NOT_FOUND` означает отсутствие проекта
или доступа к нему; следует перечитать список, не создавать пропавший проект.

Для версии 0.6 на изолированном сервере через настоящие зарегистрированные
инструменты SDK DSH проверены: список только приглашённых проектов, чтение Viewer,
отказ Viewer и Editor без разрешения агента в проверке/записи/сборке, сохранение
и запуск сборки разрешённым Editor, отказ после отключения разрешения и отзыва
доступа, отзыв личного токена. Повтор ранее успешной операции тоже требует текущих
прав. Проверка подключения гостя подтвердила, что доступ к demo не требуется;
открытие гостем выполняет только GET, а ошибки прав не вызывают повторов записи.

У `adapter_project` и `build` аргументы действия находятся внутри `request`:

```json
{"request":{"action":"open","projectId":"editorial"}}
```

После открытия можно прочитать контекст конкретной цели:

```json
{"request":{"action":"read","projectId":"editorial","targetId":"ID из analysis.targets"}}
```

Точные параметры операций берутся из `analysis.targets[].operations`. Область
`instance` относится к одному экземпляру, `component` — ко всем экземплярам
компонента, `token` — к общему токену. Ограничения и связанные цели тоже входят
в контекст. Когда нужной семантической операции нет, агент читает исходник и
использует `write_files`, сохраняя существующий стиль проекта. Исходники и
описание дизайна остаются данными проекта; технические подпромпты адаптеров
приходят отдельно в `instructions`.

Оба инструмента изменения принимают необязательный `action: "check" | "apply"`.
По умолчанию выполняется `apply`; предварительная проверка не обязательна.
Они передают `rebase: "if-unchanged"`: старая `baseRevisionId` допустима, если
**все затрагиваемые файлы целиком не изменились**. Правки другого файла не
мешают сохранению. Для семантической операции проверяется весь исходный файл
цели, даже если меняется одно свойство. Изменения разных участков одного файла
не сливаются; при конфликте ни одна часть запроса не сохраняется.

`check` возвращает `ready`, `conflict` или `already-applied`, текущую ревизию,
затрагиваемые файлы и конфликты. Это проверка на момент ответа, без записи и
резервирования. Если после неё файл изменится, `apply` может вернуть конфликт.
`already-applied.savedResult` подтверждает ранее выполненное сохранение.

Host создаёт `operationId`, если аргумент не передан. Для `check` → `apply`
или повторного обращения после потери ответа передайте возвращённый UUID и
**тот же payload, базовую ревизию и хеши**. Действие check/apply в ключ запроса
не входит. Изменённый после осмысления запрос получает новый ID. Автоматических
повторов записи нет; для исходного demo сохранён прежний один транспортный
повтор с тем же ключом и payload. В ошибках новых инструментов сохраняется ID
запроса, включая ошибки связи и несовместимости.

При `CHANGE_CONFLICT` агент получает `revisionId`, `baseRevisionId` и до трёх
записей `conflicts` с путём, кодом `FILE_CHANGED` и хешами базы/текущего файла.
`RESOURCE_CONFLICT` с `BASE_HASH_MISMATCH` означает, что переданный expectedHash
не соответствует указанной базе. В обоих случаях нужно перечитать проект и
переоценить правку; простой подмены ревизии или хешей для повтора недостаточно.

На изолированном сервере через зарегистрированные инструменты SDK DSH проверены
сохранение при правке другого файла, конфликт всего файла, отклонение пакета
правок целиком и получение прежнего результата по тому же operationId.

`saved: true` подтверждает сохранение; поля `baseRevisionId`,
`appliedOnRevisionId` и `rebased` показывают, на какой базе правка была рассчитана
и куда применена. Только `status: succeeded` подтверждает сборку. Исходник с
ошибкой может сохраниться; диагностика анализа/сборки позволяет его исправить,
а Studio сохраняет предыдущий работающий предпросмотр. Отмена и потеря ответа
не доказывают отсутствие записи — нужно прочитать состояние после восстановления
связи. Сигнал отмены DSH соблюдается; HTTP-запрос ограничен восемью секундами.

Версия 0.6 требует `access.project-roles.v1` для подключения и всех запросов.
Инструменты чтения и сборки дополнительно проверяют `adapters.source-editing.v1`.
`edit_target` и `write_files`, включая `check`, требуют
`adapters.checked-rebase.v1`. Без него запрос отклоняется с `INCOMPATIBLE`;
плагин не переключается на другой режим записи. Исходные demo-инструменты и
`/vishvakarma` сохраняют API `v1-prototype-1`.

`CONFLICT`/`CHANGE_CONFLICT` — перечитать проект; `UNAUTHORIZED` — проверить или
перевыпустить токен; `RECONNECT_REQUIRED` — подключиться к новому адресу/установке;
`TRANSPORT`/`UNAVAILABLE` — восстановить сервер и перечитать состояние;
`INCOMPATIBLE` — проверить поддержку сервером нужной возможности;
`QUEUE_FULL` — дождаться текущей сборки. При отсутствии Browser-пакета команда
открытия сообщает, что панель нужно включить.

## Устройство

Host регистрирует инструменты и файловый provider скилла. Client регистрирует
одно действие в штатном меню команд; URL Studio получает через Typert Remote,
затем вызывает `sidebarRight.openTab('browser', ...)`. Передаётся только адрес
и состояние доступности. Скилл находится относительно установленного пакета,
пользовательские каталоги скиллов не меняются.

Схемы API принадлежат серверу. `contracts/index.ts`, `runner.ts`, `adapters.ts` и `access.ts` —
его неизменённые копии; `contracts/source.json` содержит версию и SHA-256 каждого
файла. Сборка проверяет хеши копий. При изменении серверного контракта обновляйте
копию и её запись в source.json вместе, сверяя источник.
Общего workspace и импортов исходников соседнего репозитория нет.
